Deckhand Architecture Atlas

Every layer, every command path, every diagram — how the methodology, control plane, try-on engine, AI draft, and proven-path machinery connect. Built from a five-agent parallel read of the full skill source.

1What Deckhand is

One-sentence charter, then the mental model.

Deckhand converts an owner's intent into a production business they own — their VPS, their domain, their code, their data. The owner supplies decisions and the few facts only they hold; the agent supplies everything else; every claim of progress is a script result, never an assertion.

Mental model in one paragraph. Deckhand is a deterministic state machine (9 phases, 4 owner gates) wrapped around a Python CLI (dh) that owns all state on disk, plus a separate Node engine (tryon) that performs live component swaps with zero model calls per click. The AI agent never improvises the process: it asks dh next, does exactly the one thing printed (one reference file + applicable lessons), proves completion with dh phase done, and repeats. The owner only ever interacts at gates, pending asks, and the try-on browser UI.

The agent does

  • Words: copy, research claims, plan prose, brief answers
  • App-specific logic the scripts can't know
  • Exactly one AI draft per request (script-gated)
  • Everything via dh/tryon commands whose output is the proof

Scripts do (deterministic)

  • State machine, checks, gates, resume, suggestions
  • Try-on swaps, token wearing, transplant, keep/bake
  • SEO writes, slop scoring, plan lint, verify rows
  • Deploy/smoke, vetting, learning, autopsy

3The 9-phase state machine

The spine of everything. Fixed order; a check gates every step; state lives in .deckhand/run.json.

The loop: dh next → do what it prints (it names ONE reference file in read, that phase's steps in do, the preflight lessons that apply) → dh phase done <phase> (runs the phase's check; red = not done → exit 1 CHECK_FAILED, the phase stays pending; --force "<reason>" records it done anyway, marked forced) → dh next … State events (init · phase_done · phase_skip · gate · reopen · workflow) append to .deckhand/history.jsonl; every command except run · autopsy · next · status · resume · note · suggest is logged separately in .deckhand/runs.jsonl. Marking a phase done while any earlier phase is neither done nor skipped is refused OUT_OF_ORDER (exit 1); in phased mode a phase whose owed gate is still unpaid is refused GATE_BLOCKED (exit 1) — auto mode has no blocking gate, and a skipped optional phase never blocks.

4Modes & paths

Asked once at define (dh init). Both change what happens next.

Modes

  • phased (default, recommended first business): the run stops at G1–G4 until the owner says go. Quote is mandatory.
  • auto: gates pass themselves (logged by:"auto"); only genuine forks, owner-only facts and failures stop the run.

Paths (base strategy)

  • pool — vetted permissive-licence template via dh clone
  • mine — owner's own harvested base (ranked first)
  • existing — dh adopt their repo/folder; history kept, nothing rewritten
  • scratch — dh scaffold + dh compose --sections … --copy copy.json

SEO default varies by path: scratch/existing → apply by default; pool/mine → strong recommendation as a DECISION NEEDED before launch. Owner changes their mind → dh reopen <phase>.

5Gates G1–G4

The only places the owner holds the pen. Hard in phased mode — "even when the work looks obviously right".

GateMeaningBlocksArtifact shown + ONE question
G1The plan (page map + features) is approvedno clone before G1PLAN.md (+ base choice)
G2Owner opened the local app and says gono rebrand/extra work before G2local URL + logins table per role
G3Design (brand + try-on) approvedtryon is optional; skip auto-passes G3the design / try-on result
G4Go live: deploy to the serverno deploy before G4VERIFY.md

How a gate passes — deterministic quote classifier

dh gate pass G1 --quote "<owner's words, verbatim>"   # phased mode: --quote REQUIRED

The quote runs through a regex classifier → approve | approve_with_changes | change_request:

  • approve "go", "ok", "yes", "approved", "looks good", "lgtm", "ship it", "go live", "go ahead", confirm(ed), "do it", "let's go", "g[1-4] ok" + fr/de/es/ar equivalents + the thumbs-up / check emoji. "No problem / no worries" is stripped before matching — still a go.
  • NOT a go change / make it / but / however / add / remove / fix / not yet / should / must / wrong / redo — these words make it a change request
  • hold = no go "don't ship it", "wait", "hold", "stop" — a held go is not a go
  • strong-go carve-out: only an explicit strong approval ("G1 ok", "approved", "ship it") may carry a change and pass as approve_with_changes — then the change is recorded (dh note decision) and executed next phase. A bare "ok but add…" = change request (the recipe embeds their words truncated to 80 chars).
  • When in doubt → change request: the gate asks again rather than passing on a "no". A change request returns CHANGE_REQUEST with a do: recipe = dh reopen <phase> --reason "<their words>" → change → show again → ask again.
Never paraphrase an owner into approval. (Embedded incident D2 in the source: an agent once passed G1 on its own paraphrase of "make it like a real business".) Gate pass records by:"owner" + the verbatim quote; the workflow autopsy flags any gate passed without the owner's words.

6Phase-by-phase detail

What the agent does, what the owner does, what artifacts appear — per phase.

① define

Agent: dh profile doctor (record access; profile fields are answers — never re-asked) → dh workflow query → owner picks 1 of 3 workflows (or none) → draft every inferable brief field marked assumed[] → ask the rest in ONE batched message with defaults (mode, path, deliverable, languages, hosting…). Owner: answers "1a 3b" or "default". Artifacts: .deckhand/brief.json, mode/path in run state, for as scope in profile.json, PENDING.md, dh note decision for every chat choice, dh pending add … --when for later-phase questions. Exit: 5-line read-back → dh phase done define (no gate).

② research

Agent: one dh research brief --focus F --agent ID per focus (competitors | pricing | audience | conversion | discovery | local-rules | vocabulary); solo or ≤5 parallel agents, each writing ONLY its own .deckhand/research/agents/ID.json + registering pages via dh research add URL (thin notes refused; seen first to avoid double reads). Claims labeled VERIFIED / SECONDARY / INFERRED / NOT_FOUND with verbatim quotes (the verifier caps them at 400 chars; the card advises ≤300). dh research verify re-fetches every URL and fails quotes not on the page. Owner: may decline → dh phase skip research. Rules: no copying competitor copy; every conversion play becomes a section/feature or lands in features.later with reason.

③ plan

Agent: map conversion plays → pages; pool/mine path takes top base and seeds routes from it; write sitemap.json (target grammar: route: · anchor: · modal: · api: · external: · state: · mailto: · tel: · download:); loop dh plan lint to 0 errors; dh plan render → PLAN.md + mermaid; dh plan split --agents N → work packages; scratch path writes copy.json now. Owner: sees PLAN.md → one question → G1.

④ build

Agent: path entry (clone/adopt/scaffold/base record); swap rented vendor services first if env validated at build (dh swap scan → one vendor at a time → dh swap check; payments = KEEP); services via dh dev port/add/start; solo = WP by WP (WP-00 first) or team protocol (§32); everything through dh run -- …. Owner: opens URL, tests → G2 message = URL + logins table + ONE question.

⑤ brand

Agent: dh rebrand scan → dh brief set brand.* → dh rebrand apply --dry → copy pass (dh slop brief first, then rewrite from copy.json/brief) → dh rebrand check to 0 blocking → SEO step (§22): model writes copy.json → seo.pages, scripts write robots/sitemap/canonicals/OG/JSON-LD/404/llms.txt/IndexNow. Never: edit LICENSE/NOTICE/THIRD_PARTY_NOTICES; stock photos as the business; fake testimonials.

⑥ tryon optional

Owner clicks elements of the running site; N licensed variants are written into source once wearing the site's tokens and carrying the owner's copy; ←/→ compares instantly; Keep bakes + records licence. AI drafts only on request, script-gated. Exit: no open sessions. → G3.

⑦ review

Agent: tryon clean → dh verify (builds, serves production build, checks every row) → fix red blocking rows at root, never weaken checks → show VERIFY.md. Blocking rows: typecheck, build, prod-clean, tryon-closed, secrets, env-ignored, logs-ignored, swaps, honesty, product-kit (products), routes (static public, <400), seo (launch-breakers) — plus prod-serve when the production start fails. Advisory: lint, a11y-basics, deps-audit, copy-slop. Security floor before G4: rate-limited auth, server-checked admin, upload limits, CSP, no debug endpoints. → G4.

⑧ deploy

Runbooks in references/ops/. dh deploy target --app UUID --url U; every release: dh deploy ship = clean tree → push → Coolify → wait for THIS commit → smoke (200 + brand name) → deploy.json. After domain live: dh brief set domain → dh seo apply → ship (IndexNow ping) → dh seo audit --url. dh handoff → HANDOFF.md (URL, secret locations, commands, bots, verify summary, open PENDING, licences).

⑨ operate

Change loop: edit → dh verify → conventional commit → dh deploy ship → report with smoke evidence. Never edit production directly. New session: dh resume (+ --check before shipping). Bots: dh ops suggest → dh ops add (live only after it fires once). Learning: dh run --fix, dh autopsy --apply, dh autopsy --workflow. Reuse: dh harvest --name BASE --push.

8Owner communication protocol

  • Every ask is labeled: DECISION NEEDED — question (options, recommendation) · ACTION NEEDED — P-0NN: exact steps + WHERE · FYI. Never two rounds for the same fact. An ask the owner must decode was written wrong.
  • Human tasks are written the moment they appear (dh pending add, same message as the ask): project items → PENDING.md; the owner's own accounts/infra → ~/.deckhand/pending.md (--machine).
  • Every report ends, in order, with: 1) Waiting on you — open items of both ledgers with age; 2) Next (optional) — the computed suggest lines (NOW · SOON · LATER, what, why, exact command — never invented; dh suggest dismiss ID quiets one); 3) the WORKFLOW … line when a workflow is pinned.
  • At each gate: show the artifact, ask ONE question.
  • Register: terse, evidence-first, no tutorials/recaps/option surveys the owner didn't ask for; one recommendation per decision with the reason in one line.

9The dh next loop

The agent's single source of "what now". Decision logic traced through guide.py.

The observe hook — why workflow steps tick themselves

After every successful dh command (except next/status/resume/note/workflow/autopsy/suggest), _observe normalizes it (dh <sub> <action>) and matches it against the pinned workflow's pending do/check/gate steps → auto-ticks done. A state-changing command no step named is recorded as an unplanned deviation — leaving the path is recorded, not hidden. dh phase done|skip closes the remaining steps: ask/write/delegate/optional → done, the rest → skipped with a not-run deviation, and gate steps are left for dh gate pass.

The refresh hook — why RESUME.md is never stale

After every command (in a finally block, even on failure; except resume/note themselves), RESUME.md is regenerated from project files. Also for clone/adopt/scaffold's target project. So any AI, any session, any harness starts by reading one file that re-proves itself: dh resume.

12Resume · suggest · pending

The three mechanisms that make Deckhand survive session boundaries.

RESUME.md — cold start for any AI

Regenerated after every command from project files (never from memory): stage, exact next command, what is done with proof, what's in progress, owner decisions, what waits on the owner, timeline, git HEAD + dirty files, open try-on/tune/draft sessions, services up/down, last failure + known fixes. Line 4 is the verdict:

SAFE TO START A FRESH SESSION = yes iff (a) no dirty file modified after the last note, AND (b) no unexplained later failure (non-guard fail, never succeeded afterwards, after last note, no known fix). dh resume --check re-proves claims against reality (re-runs phase checks, G1 drift by mtime, app answers, verify/deploy commit == HEAD, sessions closed) — any drift → exit 1 DRIFT.

fresh_session signal: last history event is a gate AND safe() → dh next says a fresh session is safer/sharper; tell the owner.

suggest — computed, never invented

20 deterministic rules read local files only (run state, history, runs.jsonl, safety facts, pending ages, autopsy reports, brief/verify/seo/deploy, git, services, session size) → scored NOW ≥80 / SOON ≥50 / LATER. Top 3 shown (unless --all), deduped against what dh next already prints, dismissals honored (default 7 days). Examples of scores: unsaved work 95, gate 88, deferred pending due 86, services down 85, repeated failure 82.

pending — the two ledgers

One line format: - [ ] P-0NN · what · WHY · HOW · WHERE · asked date [· when: trigger]. add requires HOW+WHERE (refuses secret-shaped text). --when sets nag:no → deferred until the named phase/gate is reached → fires as a suggestion at score 86. P-SEO-* items can't be hand-closed — they re-derive from dh seo audit. Every report ends with open items + age.

13Try-on architecture

Live component swap with zero model calls per click. The agent is NOT in the click loop — do not poll.

Protocol facts. Server is loopback-only with a per-run token; API requires x-dh-token (cross-site can never call it); typed refusals return HTTP 200 {ok:false,code} so the owner sees no red console errors; all writes go through one serial queue so two clicks can't interleave; SSE /__dh/events streams progress. Overlay re-attaches every 1s if a framework wipes the body.

Setup once → serve → the owner's loop → keep/discard → clean before release.

15Variant pipeline

From 1,247 indexed components to a build-verified wrapper edit in one deterministic pass. Owner content is extracted from the clicked element before any candidate is staged.

Wrapper vs section. A wrapper component (renders children) keeps the owner's JSX inline and just empties demo props. A section gets parameterized: the design's static text becomes content.* slots and the owner's units are bound into them. Fit ratio = carried/total units — shown to the owner as "your content 8/8".

16Transplant engine

transplant.mjs — a 1,609-line three-pass deterministic transform. The heart of "variants wearing your copy".

  1. Pass A — extractUnits(owner element): AST-walk the clicked subtree → content units in document order with roles (heading, text, action, price, figure, quote, label…); deepest text host kept verbatim; module-level literal arrays and .map() loops unrolled into concrete items; forms/inputs/images captured; outputs shape + content-count (the fit denominator).
  2. Pass B — parameterize(candidate): find the component function + returned JSX, inject a typed content prop; cut embedded chrome (headers/navs; a nested <main> becomes a plain block); static text → {content.heading1 ?? <>demo</>}; demo arrays → list slots with fallback; prop defaults → slots; conditional chrome → show/hide keys; record form-swap and logo-row decisions.
  3. Pass C — bind(owner, candidate): pair units → props by role + order with heuristics: footer columns flattened to label+href lists; whole <form> swapped in place (else variant not offered); comparison tables filled row-by-row; role degradation (quote→text if needed); whole-item list placement — never half a testimonial; card groups pick the smallest row group that fits, unused rows hidden whole; owner logos replace demo brands. Returns carried / dropped / demo leftovers.

The engine writes the resulting usage <Local content={{heading1: <>…</>, list1: […]}} /> into the wrapper. Sources for links/menus: copy.json footer/nav, sitemap nav + page titles, brief brand social/name.

17Keep / discard / save

What happens when the owner commits — and how reversibility works.

Keep (bake)

  1. Extract chosen variant from wrapper → replace wrapper with it → rename tagged imports → re-parse → write
  2. Graduate folder: components/dh-tryon/<slug> → components/sections|ui-kit/<slug>
  3. bake: inline literal copy INTO the component — ?? fallbacks → owner literals; show/hide resolved (hidden demo buttons deleted, not dormant); lists rewritten with owner items; only usage-scope expressions stay as props → then prune unused imports/files
  4. Strip demo marks; leftover design-own words → .deckhand/demo-copy.json (rebrand check blocks on them)
  5. recordNotice → THIRD_PARTY_NOTICES.md (dir · title · registry · licence · sourceUrl). AI drafts exempt (header already carries provenance)
  6. Losers deleted, their CSS removed, session → kept

Discard / undo semantics

  1. File unchanged since try (sha match) → byte-exact restore from backup
  2. File edited meanwhile → surgical unwrap: keep variant 0, remove marked imports, preserve owner edits
  3. Variant folders + CSS blocks cleaned; session → discarded
  4. Installed packages stay (never silently reverted) — reported as installedKept
  5. Save to library (kept only): final dir → ~/.deckhand/library/ + index row ranks +60 next time; refuses NO_LICENCE or credential-shaped values
Dev tooling never ships. Stamps/loader are dev-only (Next plugin applies only in NODE_ENV=development). tryon clean unwires configs byte-exact (or surgically strips markers if the owner edited them), keeps the token layer only if a kept section uses it. dh verify has the blocking prod-clean row.

18Registry vetting & fit checks

Nothing enters the catalog unvetted. Refused registries stay refused.

Registry vet — 5 hard criteria (any fail → refused, with reason + what WOULD be accepted)

  1. not refused — host not on the refused list (AGPL / Commons Clause / paid tiers / bot walls)
  2. licence — SPDX from GitHub API or LICENSE file (Commons Clause checked first, never guessed) ∈ accepted set
  3. schema — shadcn-schema index (items typed ui|block|component)
  4. usable — ≥1 item maps to a try-on slot
  5. free — sample items download with real source; 401/402/403 or content-less = paywall → refused

Fit check — offline proof a design actually works here

Builds a throwaway scaffold site per base (Next + Tailwind 4 + radix-ui umbrella + Button, or the Base UI equivalent), with reference owner sections, then stages each sampled design through the same engine.stageCandidate used in a real try — so what passes is exactly what the owner gets offered. Verdicts: fits · partial · refused · broken · unreachable · unchecked → recorded to data/checks/<reg>.json (shipped) or ~/.deckhand/catalog/checks/. rank() hides broken, sinks refused.

Flags

19AI draft

Brief rules the agent must follow (written into every brief)

  • Write ONE component using EVERY owner unit verbatim — invent no facts (no numbers/prices/names/reviews/logos/claims/dates; short UI words allowed and labelled AI-written)
  • Token colour classes only — no hex/rgb/hsl/oklch/arb

20Tune & Site theme

Adjust instead of replacing — deterministic, previewed exactly, reversible byte-exact.

Tune — one element

  • Dials: density, size, weight (−2..+2) · corners sharp/soft/as-is/round/pill · depth flat/subtle/as-is/raised · contrast soft/as-is/crisp · width −2..+2
  • Presets: quieter · bolder · airy · compact · clarity · softer · sharper
  • Each knob = a Tailwind class-token transform (spacing ×0.6..1.5, text steps, weight ladder, rounded ladder, shadow ladder, max-w ladder) applied to className literals in the picked element's subtree
  • Sessions: original snapshotted to tune/<id>.orig; every set recomputes from the original (no cumulative drift); re-parses before write; refuses if file changed (FILE_CHANGED)
  • Reset: untouched → byte-exact restore; owner edited meanwhile → surgical (swap back only the class pairs the knobs changed)
  • Chat path: owner says "make the hero airier" → agent runs tryon tune --preset airy … → owner checks HMR → --keep / --reset

Site theme — whole look

  • Knobs: accent (10 curated swatches or any hex/oklch) · neutrals as-is/neutral/warm/cool · corners sharp/soft/round/pill → --radius · density compact..spacious → --spacing · headlines smaller..display → text scale · body/heading fonts (13-font curated list)
  • Computed light+dark variable values are exactly what apply writes (overlay previews the same)
  • Apply: strips previous /* dh:theme */ block, appends new one at end of globals + next/font AST rewrite in root layout
  • Undo: snapshots into theme/history.json, 10 applies deep, byte-exact restore
  • Vite gets every knob except next/font

23Slop — does this text read as AI?

Deterministic script, 11 language packs, same text → same verdict. No model call.

Pipeline

(a) dh slop brief [--lang L]   # BEFORE writing → avoid-list + 5 rules
(b) model writes the copy
(c) dh slop check [PATH… | --text T | --url U]   # → clean | review | slop

Scoring: weighted hits per 100 words (strong tell 3, buzz 1, phrase w, unnumbered superlative 2…) → thresholds clean <4 · review ≥4 · slop ≥10; any single strong hit → at least review; kind:"leak" (chatbot voice pasted on a page) → always slop. Language-free signals (any language): em-dash/exclamation rates, decorative emoji, flat sentence rhythm. Transitions and triads only fire when a language pack defines them.

Three overlay layers: shipped packs (data/slop/<lang>.json) · personal overlay via dh slop add · project allowlist via dh slop allow "brand word" — brand words never slop on their own site; a line marked dh:slop-ok is never read.

Where it gates: dh rebrand check blocks on slop verdict (review → warn); dh compose runs it on copy.json before the owner sees words; dh verify runs copy-slop on rendered pages (advisory). Pack self-test: every pack's own slop examples must score slop and clean examples must score clean (dh slop lint).

24Workflows — proven paths

A pinned workflow turns dh next into step-by-step instructions with built-in proof.

Query → pick → pin

At define, dh workflow query scores every workflow against the brief — a pure function: deliverable +40 · industry +30 (or same family +20) · shape +15 · features min(30, 10×hits) · proven on this harness +10 · this OS +10 · level trusted +15/proven +5/draft −15 · source mine +50 / community-unreviewed −10 → top 3 with reasons, proof, and what they miss. Owner picks one (or none) → dh workflow use REF pins {id, version, source, sha, params, done[], skipped[], deviations[]} into run.json. Re-pinning the same id+sha keeps progress (survives compaction).

Schema (deckhand.workflow/1)

  • match (deliverable/shape/industry/family/features/stack/path) · proof.runs[] (date, harness, os, complete, errors, minutes) · params (defaults + why) · ask_upfront[] (questions asked at define, learned from past runs)
  • phases[] → steps[] — each step exactly one kind: do | ask | write | delegate | check | gate; do/check/gate require expect (what the command must print = the step's proof)
  • pitfalls[] (sig + fix, matched when that step's commands fail) · creative[] (what the workflow does NOT decide — the model's creative room) · changelog[]

Proof levels are computed, never declared: draft (no complete green run) → proven (≥1 complete run, 0 errors) → trusted (≥3 green runs on ≥2 distinct harnesses OR ≥2 distinct OSes + reviewed).

Step ticking

Automatic: the observe hook (§9) ticks matching steps after each command; stateful commands no step named → unplanned deviation; dh phase done closes the rest. Manual: dh workflow step ID done|skip --why (skip needs why → deviations). Checklist: dh workflow todo --format md (harness-neutral). Status line embedded in every report: WORKFLOW id@v (level) · phase-id done-in-phase/total-in-phase · done/total steps · n deviations · p proposals waiting (proposals clause only when p>0).

Creation & improvement

dh workflow new --from-run extracts this run's phases + successful stateful commands + learned questions (deterministic, owner facts never copied). dh autopsy --workflow → timeline / questions (LATE, DIRECTION-CHANGE, LOST) / deviations / errors / delegation / guidance / proposals → owner picks where they go: dh workflow save --from-autopsy W --proposals P1,P3 [--public] (my pool / community PR / nothing) — adds this run as proof, bumps version. Lint rejects private commands, absolute user paths, curl|sh, rm -rf /, secret-shaped values, unknown dh subcommands (hard for base/community; warnings for mine, --accept then needed). >120 steps is a "split it" warning. Pools resolve mine → base → community (community sha-verified, offline never errors).

25Research pipeline

Parallel-safe, quote-verified, efficiency-scored. Competitors, pricing, audience, conversion plays — with receipts.

  1. Brief: one dh research brief --focus F --agent ID per focus — carries budget, questions (TARGET · PRIMARY · DONE_WHEN · FRESH), pages already seen, vocabulary so far, claim-id prefix.
  2. Card loop (research-card.md): before a search → dh research seen URL; open a page only when snippet is TARGET/PRIMARY; diagnose results → ONE change → re-query (never reword a failed query blindly).
  3. Add: dh research add URL --by ID --note "dense facts" — thin-note guard (NOTE_TOO_THIN), per-agent dedupe, other agents' prior notes returned. Each agent writes ONLY its own agents/ID.json; sources append to shared sources.jsonl (no race).
  4. Merge: single-writer fold into research.json (bad JSON → nothing merged; dup claim ids → error).
  5. Verify: structural checks (labels, url+quote for VERIFIED/SECONDARY (quote ≤400 chars; the research card advises ≤300), vocabulary terms must contain themselves, INFERRED needs from[], NOT_FOUND needs tried) → re-fetch every URL (cache, PDF → unchecked, blocked statuses) → NFKC-normalized quote match → ok = 0 mismatch, 0 invalid, 0 bad vocabulary.
