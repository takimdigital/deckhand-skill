Deckhand try-on — real-browser test report

Eight sections swapped, an AI draft taken end-to-end, tuning/theme/flags/keep verified against source hashes — all driven in headless Chromium against a real Next.js site.

Verdict works with 1 blocker

Component swapping works: slot guessing was correct on 8/8 sections, 7/8 staged 4 variants each, cycling between them performs zero file writes, and every discard restored the source byte-exact. The AI draft path is complete (request → gates → labelled variant → keep). Watching/HMR renders source edits in ~514 ms without a reload.

But one blocking defect: staging the shadcnui-blocks/footer-01 design takes the whole page down (HTTP 500) while try reports ok:true, exit 0 — see §8. Six further behaviours are worth correcting in the atlas (§9).

Review of this report (second pass) checked in a real Next 16 lab

Every finding below was re-checked against the code and, for the blocker, reproduced on a real Next.js 16.3.6 dev server. What changed:

  • The blocker was real and is fixed. Not only footer-01: footer-02 and footer-03 crashed the same way (see the call stack in Fig 15). Cause: with no menu in the plan the design's demo columns are emptied, and the owner's columns were merged over an empty template, so links was undefined. The merge now spreads the item's empty arrays first; all three footers render, page 200.
  • §8's explanation of the safety net was wrong. The check does catch a render error: a 500 is a build error to it, and with --url the lab's run dropped the three footers and restored the file. It did not fire here because try was run with no dev URL, so nothing was checked. try now says so (verified:false with a note), and when every design that fits broke the page the error says that instead of "no candidates".
  • Fixed as well: stranded variant folders are swept on discard (§8), picking an element already in a try says SESSION_OPEN (§9.5), sub-actions work after the options (§9.6), one draft rejection lists every problem (§9.7), SVG attributes are written the React way (§9.8), clean takes back its .gitignore lines, CRLF too (§9.10), the fixture site has a root layout and PostCSS config (§9.11), and a busy port says PORT_BUSY (§9.12). Each ships with a test.
  • Confirmed as designed, no change: Compare on by default (§9.2), the pre-guessed slot (§9.3), "AI draft only" slots (§9.4), demo logos marked (§9.9), stampsInHtml until the restart clean asks for.

8 · BLOCKER — staging a footer design returns HTTP 500

Reproduced 3 ways: browser, CLI, and plain HTTP

The design shadcnui-blocks/footer-01@radix is offered as footer variant 4. When it is written into the wrapper it crashes during React Server Component rendering, and because every variant in a wrapper is rendered (the inactive ones merely display:none), the entire page stops rendering.

The pipeline reports success anyway: try returned {"ok":true,"id":"s7278c",…} with exit 0 and left the session open, while the page was already down.

The engine's own fit data explains it: that variant reported hidden: ["footerSections: the design's demo columns hidden (6) — no menu in your plan"]. Hiding the demo columns leaves the array the component then calls .map() on as undefined.

Why the documented safety net did not fire corrected on review

Review: the explanation below is wrong. try was run without --url (and without dh dev start), so no page was loaded at all. With a dev URL the check treats the 500 as a build error, drops the culprits and restores the file. The first paragraph is kept as written.

The atlas's Fig 15.1 step 6 claims openVerified does "parse → ONE wrapper write → probe page → build error? exclude culprits, retry ≤2 (3 attempts) else restore the file". Here the compile succeeds and the render fails, so the probe passed and the file was left in place. Through the browser the overlay then sat waiting for [data-dh-session] and hit a 420 s timeout with pageErrors: ["Cannot read properties of undefined (reading 'map')" ×2].

Second defect from the same run — orphaned files

When staging fails mid-way, the variant folders it already wrote are stranded: 5 directories under components/dh-tryon/ were referenced by no session at all (shadcnui-blocks-footer-02, shadcnui-blocks-footer-03, smoothui-footer-1, tailark-oss-mist-footer-3, tailark-oss-veil-footer-3), and a later discard could not remove them because it only knows what its session recorded.

Workaround

discard restores the file byte-exact and the page recovers immediately (200). The safe path today is to avoid shadcnui-blocks/footer-01, or to stage with --only excluding it.

Claims that held up completely

  • Zero model calls per click — cycling is pure DOM; 0 file writes measured on all 7 working sections.
  • Loopback-only + per-run token — :4010 refused on the LAN IP while the dev server bound ::; requests without x-dh-token → 403 BAD_TOKEN.

  • Byte-exact reversibility — discard, tune reset, theme undo, clean unwire all restored exact sha256s.
